# Module 15 — Normalization & Design

## Module Goal

By the end of this module, you will be able to look at a badly designed table — one riddled with repeated data and update anomalies — and explain precisely *why* it's wrong, using formal vocabulary (functional dependency, partial dependency, transitive dependency) rather than a vague feeling that "something about this looks off." You will be able to systematically decompose such a table through the normal forms (1NF, 2NF, 3NF, BCNF), and, just as importantly, design a correct table structure from scratch using entity-relationship (ER) modeling before you ever type `CREATE TABLE`. You will also learn when to deliberately break these rules — denormalization — and understand exactly what risk you're accepting when you do. Every table you've built in this course so far (Module 4, Module 5) was handed to you already reasonably well-shaped; this module teaches you the theory that lets you shape one yourself, correctly, from a messy real-world requirement.

## Topics Covered in This Module

1. **[Functional Dependencies](01-functional-dependencies.md)** — The formal notion that one column's value determines another's, worked out from a realistic messy table, and why this single concept underlies every normal form that follows.
2. **[First Normal Form (1NF)](02-first-normal-form.md)** — Atomic values, eliminating repeating groups and array-like columns, with a concrete before/after transformation.
3. **[Second and Third Normal Form (2NF, 3NF)](03-second-and-third-normal-form.md)** — Eliminating partial dependencies (2NF, relevant only when a table has a composite key) and transitive dependencies (3NF), each worked through a before/after decomposition.
4. **[Boyce-Codd Normal Form (BCNF)](04-boyce-codd-normal-form.md)** — The narrow edge case 3NF misses, why it's described as a stricter version of 3NF, and a worked example of a 3NF table that still isn't BCNF.
5. **[Entity-Relationship (ER) Modeling](05-er-modeling.md)** — Entities, attributes, relationships, and cardinality; how many-to-many relationships are implemented with a junction table; translating a full ER diagram into `CREATE TABLE` statements.
6. **[Denormalization Trade-offs](06-denormalization-tradeoffs.md)** — Deliberately reintroducing redundancy for read performance, when it's justified, and the update-anomaly risk it brings back.
7. **[Module Summary](07-module-summary.md)** — Consolidated recap.

## Prerequisites

- **Module 2 — Relational Model**, especially [Tables, Rows, and Columns](../02-relational-model/01-tables-rows-and-columns.md): you need the vocabulary of a relation as a set of tuples with named attributes, since every definition in this module (functional dependency, normal form) is stated in terms of a relation's attributes.
- **Module 5 — Constraints & Keys**, especially [Primary Keys](../05-constraints-and-keys/03-primary-keys.md) and [Foreign Keys and Referential Integrity](../05-constraints-and-keys/04-foreign-keys-and-referential-integrity.md): normalization is, at its core, a precise theory about how every non-key attribute must relate to the *whole* key, not part of it — you cannot meaningfully talk about "2NF" without already knowing what a candidate key and a composite key are and what it means for a key to uniquely identify a row (a concept this module leans on constantly, alongside the uniqueness guarantees covered in [UNIQUE Constraints](../05-constraints-and-keys/02-unique-constraints.md)).
- **Module 10 — Joins & Set Operations** ([Joining Multiple Tables](../10-joins-and-set-operations/05-multiple-table-joins.md)): normalization's entire payoff is that splitting data into smaller, non-redundant tables is *safe* only because joins let you reliably reconstruct the full picture on demand. If joining multiple tables back together still feels like unwelcome extra work rather than a natural, cheap operation, this module's trade-offs won't feel justified.
- **Module 4 — Database & Table Design** ([Creating Tables](../04-database-and-table-design/02-creating-tables.md)): every worked example in this module ends in an actual `CREATE TABLE` statement, including composite primary keys and foreign keys, so you should already be comfortable with basic `CREATE TABLE` syntax.

## How to Study This Module

Topics 1 through 4 form one continuous story and should be read in strict order — each normal form is defined in terms of the functional dependency vocabulary Topic 1 builds, and 2NF, 3NF, and BCNF are progressively stricter versions of the same underlying idea (no non-key attribute should depend on anything less than, or other than, the whole key). Don't skip ahead to BCNF hoping to shortcut 2NF/3NF — the entire reason BCNF is *interesting* is that it catches a narrow case those two miss, which only makes sense once you've internalized what they already catch. Topic 5 (ER modeling) is a shift in direction: instead of fixing a bad table after the fact, it teaches you to design a good one from the start, and it reuses the exact same running example the earlier topics decomposed piece by piece, so treat it as the payoff of Topics 1–4, not an unrelated topic. Topic 6 (denormalization) deliberately runs against everything the rest of the module argues for — read it last, and read it as a controlled, deliberate exception to a rule you now understand well, not a reason to abandon normalization by default.
