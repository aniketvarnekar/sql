# Natural vs. Surrogate Keys

## Learning Objectives

By the end of this section you should be able to:
- Define a natural key and a surrogate key, and correctly classify a candidate primary key as one or the other
- Weigh the trade-offs between the two along stability, simplicity, performance, and meaning-leakage
- Explain why surrogate keys are the common default in practice
- Identify realistic scenarios where a natural key is still the better choice

## Prerequisites

- [Primary Keys](03-primary-keys.md) — this topic is a design discussion about *which* column should become the primary key, so you need to already understand what a primary key guarantees before weighing candidates for the role.
- [Foreign Keys and Referential Integrity](04-foreign-keys-and-referential-integrity.md) — several trade-offs below concern how painful it is when other tables reference this key, which only makes sense once you understand what a foreign key reference actually commits you to.

## Motivation

Every table needs a primary key (Topic 3), but *which column* should hold that role is a genuine design decision, not a mechanical one. Should a `products` table be identified by its SKU — a real-world code that already uniquely identifies the product to the business — or by a meaningless, database-generated integer that has no significance outside the database itself? Both are legitimate answers, and the choice has consequences that ripple through every foreign key, every join, and every future schema change built on top of it.

## Problem Statement

Suppose you design a `products` table using the manufacturer's SKU as the primary key, since it's already guaranteed unique by the business:

```sql
CREATE TABLE products (
    sku   TEXT PRIMARY KEY,
    name  TEXT NOT NULL,
    price NUMERIC(10, 2) NOT NULL CHECK (price > 0)
);

CREATE TABLE order_items (
    order_id   INTEGER NOT NULL,
    sku        TEXT NOT NULL REFERENCES products (sku),
    quantity   INTEGER NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, sku)
);

INSERT INTO products (sku, name, price) VALUES ('DL-100-BLK', 'Desk Lamp (Black)', 24.99);
INSERT INTO order_items (order_id, sku, quantity) VALUES (1, 'DL-100-BLK', 2);
```

This works fine — until the manufacturer reorganizes their SKU scheme, or a data-entry mistake creates the SKU as `'DL-100-BLACK'` instead and it needs correcting, or the product is later resold under a different brand with a new code:

```sql
UPDATE products SET sku = 'DL-100-BLACK' WHERE sku = 'DL-100-BLK';
```

```
ERROR:  update or delete on table "products" violates foreign key constraint "order_items_sku_fkey" on table "order_items"
DETAIL:  Key (sku)=(DL-100-BLK) is still referenced from table "order_items"
```

Because `sku` is the primary key *and* it's referenced by a foreign key elsewhere, changing it is now a nontrivial, coordinated operation — you'd need `ON UPDATE CASCADE` (Topic 4) or a careful manual migration across every referencing table. A value that originates *outside* the database (assigned by a manufacturer, a government, a person) is fundamentally at the mercy of that outside world's decisions to correct, reformat, or reassign it — yet the primary key is exactly the value every other table has been told never changes.

## Concept

### Natural Keys

A **natural key** is a column (or set of columns) that already exists as a meaningful, real-world attribute of the entity, and happens to be unique and suitable to serve as a primary key without any database-generated value. Examples: a product's SKU, a country's ISO code (`'US'`, `'IN'`), a vehicle's VIN, an email address, a national ID number.

```sql
CREATE TABLE countries (
    iso_code CHAR(2) PRIMARY KEY,   -- natural key: 'US', 'IN', 'JP', ...
    name     TEXT NOT NULL
);
```

### Surrogate Keys

A **surrogate key** is a value with no meaning outside the database whatsoever — its only job is to identify a row. It is typically generated by the database itself and never interpreted, parsed, or assigned any business meaning by anyone.

```sql
CREATE TABLE products (
    product_id SERIAL PRIMARY KEY,   -- surrogate key: 1, 2, 3, ... — means nothing outside this table
    sku        TEXT NOT NULL UNIQUE, -- the natural key still exists, just not as the primary key
    name       TEXT NOT NULL,
    price      NUMERIC(10, 2) NOT NULL CHECK (price > 0)
);
```

The two most common ways to generate a surrogate key in PostgreSQL:

```sql
-- Option 1: SERIAL (or, in modern PostgreSQL, GENERATED ALWAYS AS IDENTITY) — a simple incrementing integer
product_id SERIAL PRIMARY KEY

-- Option 2: UUID — a 128-bit universally unique identifier, useful when IDs must be
-- generated independently across multiple systems without coordinating on a shared counter
product_id UUID PRIMARY KEY DEFAULT gen_random_uuid()
```

Rewriting the earlier example with a surrogate key resolves the earlier problem entirely:

```sql
CREATE TABLE order_items (
    order_id   INTEGER NOT NULL,
    product_id INTEGER NOT NULL REFERENCES products (product_id),
    quantity   INTEGER NOT NULL CHECK (quantity > 0),
    PRIMARY KEY (order_id, product_id)
);

UPDATE products SET sku = 'DL-100-BLACK' WHERE sku = 'DL-100-BLK';
```

```
UPDATE 1
```

The correction succeeds instantly and silently — nothing else in the schema references `sku` as an identifier, so correcting it is a completely ordinary, low-stakes `UPDATE`, exactly like fixing a typo in any other descriptive column. The SKU is still stored, still enforced `UNIQUE`, and still fully usable for business lookups (`WHERE sku = 'DL-100-BLK'`) — it's simply no longer the column other tables are structurally locked to.

### Trade-offs

| Dimension | Natural key | Surrogate key |
|---|---|---|
| **Stability** | At risk — can require correction, reformatting, or reassignment by an authority outside the database (a manufacturer, a government, a person changing their name/email). | Extremely stable — a database-generated value never needs to change for real-world reasons, since it never carried real-world meaning to begin with. |
| **Simplicity of foreign keys** | Foreign keys inherit whatever type/size the natural key has (e.g., a `TEXT` SKU), and any correction cascades to every referencing table. | Foreign keys are a single, small, consistent type (commonly an integer or UUID) across the whole schema, regardless of how business identifiers look or change. |
| **Performance** | Often larger and more variable in size (variable-length text), making indexes on it and on every referencing foreign key column somewhat larger and slower to compare. | Typically compact and fixed-size (a 4/8-byte integer, or a 16-byte UUID), which indexes and joins handle efficiently. |
| **Meaning-leakage risk** | The identifier itself reveals business information (a sequential invoice number reveals roughly how many invoices exist and in what order; an email used as a key reveals a real address in every join and log line touching it). | Carries no information at all outside the database — a `product_id` of `482` tells you nothing about the business. |
| **Guaranteed availability at insert time** | Sometimes not yet known — e.g., a real-world code assigned by an external system days after your own row must already exist. | Always available immediately — the database generates it the instant the row is created, with no dependency on an outside process. |
| **Business meaningfulness** | Directly meaningful to a human reading the data — a report showing SKU `DL-100-BLK` is self-explanatory. | Meaningless to a human without joining back to a descriptive column — `product_id = 482` requires a lookup to mean anything to a person. |

### Why Surrogate Keys Are the Common Default in Practice

Given the trade-offs above, most real-world schemas default to a surrogate key (a `SERIAL`/identity integer, or a `UUID`) as the primary key, and keep any natural, business-meaningful identifier as a separate `UNIQUE` column instead — exactly as the corrected `products` example above does. This gives you the best of both: the primary key that every foreign key relies on structurally never needs to change for business reasons, while the natural key remains fully available, enforced unique, and usable for everyday lookups and reporting.

```sql
CREATE TABLE products (
    product_id SERIAL PRIMARY KEY,    -- surrogate: what every foreign key points at
    sku        TEXT NOT NULL UNIQUE,  -- natural: what the business actually looks products up by
    name       TEXT NOT NULL,
    price      NUMERIC(10, 2) NOT NULL CHECK (price > 0)
);
```

### When a Natural Key Is Still the Right Choice

Surrogate keys are the common default, not a universal rule. A natural key is still the right choice when:

- **The identifier is genuinely, provably immutable and controlled by no outside authority that could reasonably reassign it** — an ISO country code (`'US'`) is about as stable an identifier as exists; adding a surrogate `country_id` on top of it would add a layer of indirection with no real benefit.
- **The table is a small, mostly-static reference/lookup table** — a `currencies` table keyed by ISO currency code (`'USD'`, `'EUR'`), or a `us_states` table keyed by two-letter state abbreviation, rarely benefits from a surrogate key, since these values are stable, small, and already meaningful in every join.
- **Human readability in foreign keys is a genuine, ongoing operational need** — if engineers and analysts constantly write ad hoc queries and need to recognize identifiers at a glance without a join, a natural key can meaningfully reduce friction, at the cost of the stability trade-offs above.

```sql
CREATE TABLE currencies (
    currency_code CHAR(3) PRIMARY KEY,  -- 'USD', 'EUR', 'INR' — stable, small, standardized, human-readable
    display_name  TEXT NOT NULL
);
```

## Internal Working (Preview)

A surrogate key generated via `SERIAL` is backed internally by a PostgreSQL **sequence** — a separate database object that atomically hands out the next integer on every call, independent of and safely concurrent with any number of simultaneous `INSERT`s:

```
INSERT INTO products (name, price) VALUES (...);
        │
        ▼
product_id column has no value supplied → DEFAULT engages
        │
        ▼
DEFAULT calls nextval() on the table's underlying sequence object
        │
        ▼
Sequence atomically increments and returns the next integer (e.g., 483)
        │
        ▼
Row is written with product_id = 483
```

A `UUID` generated via `gen_random_uuid()` instead produces a random 128-bit value with no shared counter at all — this is precisely why UUIDs are popular in distributed systems where multiple independent processes or databases must generate IDs without coordinating with each other, at the cost of a larger, less sequential (and therefore sometimes less index-friendly) key than a simple incrementing integer. Module 13 covers the indexing performance implications of key size and ordering in depth.

## Real-World Analogy

A natural key is like using someone's home address as their permanent identifier in a filing system — it's meaningful and human-readable, but people move, streets get renamed, and every file that referenced the old address now needs updating. A surrogate key is like the arbitrary patient ID number a hospital assigns on intake — it means nothing to anyone outside the hospital's own records, but it never has to change no matter how many times the patient moves, changes their name, or updates their contact details; the hospital simply keeps a separate, freely-editable "current address" field linked to that stable, meaningless ID.

## Why Surrogate Keys Became the Common Default

This design preference follows directly from the stability problem shown in the Problem Statement, combined with what a primary key is used for once foreign keys exist (Topic 4): a primary key is not just an identifier for a row within its own table — it becomes a structural dependency for every other table that references it. A value with real-world meaning is, by definition, subject to real-world correction, renaming, and reassignment (a typo fixed, a scheme reorganized, an authority changing its own rules) — none of which the database controls. A surrogate key sidesteps this entirely by deliberately choosing a value that carries no meaning and therefore has no external force that would ever need to change it — the only entity that ever "owns" a surrogate key's value is the database itself, which is precisely the one place a primary key is supposed to be stable.

## Advantages

**Surrogate keys:**
- Never need to change for business reasons, since they carry no business meaning to begin with.
- Compact and consistent in type/size across a schema, which keeps foreign keys, indexes, and joins efficient.
- Available immediately at row-creation time, with no dependency on an external identifier being assigned first.

**Natural keys:**
- Immediately meaningful to a human reading the data, without a join.
- Avoid an extra column when a stable, well-governed real-world identifier already exists (ISO codes, standardized reference data).
- Prevent an entire class of duplicate-row bugs "for free" — two rows with the same real-world identity are structurally impossible, whereas two rows with different surrogate keys but identical real-world attributes require a separate `UNIQUE` constraint to catch.

## Disadvantages / Limitations

**Surrogate keys:**
- Meaningless to a human without a join or lookup — debugging directly against raw IDs is less intuitive.
- Adds a column that exists purely for database bookkeeping, alongside whatever natural identifier the business still needs for its own purposes.

**Natural keys:**
- At risk of needing correction or reassignment by an authority outside the database's control, which is disruptive once foreign keys depend on it (Topic 4's `ON UPDATE CASCADE` mitigates but doesn't eliminate this).
- Often larger or more variable in size than a simple integer, which can make indexes and joins on it (and on every referencing foreign key) less efficient at scale.
- Can leak business information through its own value (sequential identifiers revealing volume/order; identifiers containing personal information like an email).

## Best Practices

- Default to a surrogate key (`SERIAL`/identity integer, or `UUID`) as the primary key for most application tables, and keep any natural, business-meaningful identifier as a separate `UNIQUE NOT NULL` column.
- Reserve natural keys for small, genuinely stable, standardized reference tables (ISO country/currency codes, US state abbreviations) where the "identifier" is externally standardized and essentially never reassigned.
- Choose `SERIAL`/identity integers when IDs are only ever generated by a single database, and `UUID` when IDs must be generated independently across multiple systems or services without a shared, coordinated counter.
- Never use a column that could plausibly need correction (an email address, a user-entered code, anything a person could mistype and later need fixed) as a primary key that other tables structurally depend on via foreign key.

## Common Mistakes

| Mistake | Why it's wrong |
|---|---|
| Assuming a natural key is always "more correct" because it's meaningful | Meaningfulness is a genuine advantage, but it comes bundled with an external stability risk a surrogate key avoids entirely — the "more correct" choice depends on how stable that specific natural value really is. |
| Adding a surrogate key to every single table reflexively, even small, standardized reference tables | For genuinely stable, standardized data (ISO codes, currency codes), a surrogate key adds an extra column and an extra join with no real benefit over using the standardized code directly. |
| Using a natural key as the primary key and then being surprised that correcting a typo in it is a major operation | Once other tables reference a column via foreign key, changing that column's value becomes a coordinated, cascading operation (Topic 4) — this is precisely the stability risk that makes surrogate keys the common default. |
| Believing a surrogate key eliminates the need for a `UNIQUE` constraint on the natural identifier | A surrogate primary key only guarantees the surrogate column itself is unique — the natural key (like `sku`) still needs its own explicit `UNIQUE` constraint if duplicates in it would still be a real-world problem. |

## Interview Questions

1. **Q: What is the difference between a natural key and a surrogate key?**
   A: A natural key is a column that already exists as a meaningful real-world attribute (an SKU, an email, a national ID) and happens to be suitable as a primary key. A surrogate key is a value generated purely for database identification purposes, with no meaning outside the database — typically an auto-incrementing integer or a UUID.

2. **Q: Why do most production schemas default to surrogate keys rather than natural keys for primary keys?**
   A: Because a primary key becomes a structural dependency for every foreign key referencing it. Natural keys are subject to real-world correction, reformatting, or reassignment by authorities outside the database's control, which makes any such change to a widely-referenced primary key disruptive. Surrogate keys carry no real-world meaning and therefore never need to change for business reasons, making them far more stable as the anchor other tables depend on.

3. **Q: Give an example of a table where a natural key is still the better choice, and explain why.**
   A: A `currencies` reference table keyed by its ISO 4217 currency code (`'USD'`, `'EUR'`) is a good natural-key candidate — the code is externally standardized, essentially never reassigned, small and fixed-size, and immediately meaningful in every join, making an additional surrogate `currency_id` an unnecessary extra layer of indirection for data this stable.

4. **Q: If you use a surrogate primary key for a `products` table, does that mean the SKU column no longer needs any constraints?**
   A: No — the SKU should still typically be declared `UNIQUE NOT NULL` even though it's no longer the primary key, since duplicate or missing SKUs are still a real-world data problem the surrogate key does nothing to prevent on its own.

## Summary

- A **natural key** is a real-world, business-meaningful attribute used as a primary key; a **surrogate key** is a database-generated value with no meaning outside the database.
- Natural keys are immediately meaningful and can avoid redundant columns for stable reference data, but are at risk of needing correction or reassignment by an outside authority, which is disruptive once foreign keys depend on them.
- Surrogate keys (typically `SERIAL`/identity integers or `UUID`s) are stable, compact, and consistently typed, at the cost of being meaningless to a human without a lookup.
- Most application schemas default to a surrogate primary key plus a separately `UNIQUE`-constrained natural identifier, giving stability to foreign keys while still keeping the natural identifier available and enforced.
- Reserve natural keys as primary keys for small, genuinely stable, standardized reference data, such as ISO country or currency codes.
