## Practical Connections

- A reporting dashboard that renders a spreadsheet-style monthly-by-year table is, underneath, running exactly the conditional-aggregation pattern from Topic 1 against data stored in the ordinary long form it was inserted in.
- A product catalog spanning wildly different item types (electronics, apparel, furniture) commonly keeps universal fields (name, price, stock count) as ordinary columns and category-specific attributes in a `JSONB` column, indexed with GIN exactly as Topic 2 described, rather than forcing every possible attribute into its own nullable column.
- Every application with a "sign up" flow that shows a new user their account or order number is displaying a value ultimately generated by a sequence — and every such system has to be built to tolerate the occasional gap Topic 3 explained, rather than treating id values as a literal count of rows.
- A nightly ETL job that reshapes raw data through several dependent, checkable stages commonly uses temporary tables (Topic 4) to stage each stage's output, exactly so a failure partway through leaves nothing permanent behind and doesn't collide with another concurrent run.
- A high-traffic logging or events table with years of accumulated history, where 95% of queries only ever touch the last 30 days, is a textbook case for the range partitioning covered in Topic 5 — both for query speed and for painless retention-policy cleanup.

## Frequently Confused Concepts (Recap)

| Confused pair | The distinction |
|---|---|
| `PIVOT` (SQL Server/Oracle) vs. conditional aggregation (PostgreSQL) | PostgreSQL has no dedicated `PIVOT` keyword; the same row-to-column reshaping is achieved with an aggregate function wrapped around `CASE WHEN` (or `FILTER (WHERE ...)`), combined with `GROUP BY`. |
| `JSON` vs. `JSONB` | `JSON` stores exact input text, re-parsed on every read; `JSONB` stores a decomposed binary form, parsed once, indexable with GIN, and supports containment/existence operators — `JSONB` is the correct default almost always. |
| `->` vs. `->>` | `->` returns a JSON value (still quoted, still `jsonb`); `->>` returns plain SQL text — use `->>` when comparing against an ordinary literal. |
| `SERIAL` vs. `GENERATED ... AS IDENTITY` | Both are backed by the same underlying sequence mechanism; `SERIAL` is PostgreSQL-specific shorthand, while `IDENTITY` is the modern, SQL-standard-compliant form, with `ALWAYS`/`BY DEFAULT` controlling whether an explicit inserted value is rejected or silently accepted. |
| Gaps in sequence values vs. data loss | A gap means a value was consumed (by a rollback, or by session caching) and never used by any row — it is not missing or corrupted data, since a surrogate key's job is uniqueness, never contiguity. |
| Temporary table vs. CTE | A temp table is real, disk-backed, indexable storage reusable across multiple separate statements in a session; a CTE is scoped to, and disappears with, the single query it's part of. |
| Temporary table vs. view | A temp table is private to one session and physically materialized; a view is a permanently shared, named query, re-run on each reference (unless materialized) and visible to every session with permission. |
| `DROP TABLE partition` vs. `ALTER TABLE ... DETACH PARTITION` | `DROP` permanently destroys the partition and its data; `DETACH` disconnects it from the parent but leaves it intact as a standalone table, useful when you want to archive or double-check before actually discarding it. |
